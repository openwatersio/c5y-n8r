# Contributing

c5y-n8r provides fast library access to country information from pinned Wikidata snapshots and explicitly reviewed local contributions. Accuracy and traceability are requirements for accepting data. Our first goal is verified coverage of the country inputs required by Slackwater; `sources/slackwater-required.json` records that inventory and its pending verification status.

## Verify each assertion before editing Wikidata

For every data addition or correction, identify one high-quality primary source for the exact assertion and check it against at least two other quality sources. Read all three. Add the primary reference to the relevant Wikidata statement; retain the corroborating sources, passages and review notes in the issue and review record. Preserve valid existing Wikidata references.

Those minimums describe the existing statement-override workflow. New name and alias readiness records use the stricter requirement below: one authority plus three independent corroborating sources, all referenced on the supporting name statement. That diagnostic rule does not revise existing staged statement approvals.

The sources must support the same entity, value, meaning, and applicable time period. Prefer the responsible standards body or issuing authority as the original source. Sites repeating one dataset, mirrors of the same publication, and sources derived from Wikidata do not provide independent corroboration. Explain assessed independence and any remaining uncertainty rather than inferring independence from different hostnames. Search snippets and an AI-generated answer are not evidence.

Read the supporting passage or table in every source. Record its URL or publication identifier, section or page, publication or revision date where available, and retrieval date. Explain how it supports the assertion. For historical claims, verify the effective dates separately: a current ISO table does not establish when a code was introduced, retired, or reassigned. Preserve any uncertainty in date precision.

If the sources disagree or fewer than two other quality corroborating sources can be found, leave the assertion unresolved and document the gap. Do not update Wikidata on our behalf or accept the data into a verified release until the discrepancy is resolved and the evidence requirement is met. Never manufacture consensus by counting duplicate sources.

## Contribute upstream and preserve local review

1. Check the current Wikidata entity and statement, including its qualifiers, rank, and existing references. Confirm the entity represents the intended country or historical identity.
2. Complete the source checks above before submitting the Wikidata edit. Add the primary source as a statement reference using the appropriate reference properties. Keep corroboration in the issue and review record. For name-readiness records, also add all four sources to the supporting name statement. Preserve valid existing references and follow Wikidata's contribution rules. Keep a passage-level explanation in the pull request if the reference fields cannot capture it.
3. Record the resulting Wikidata revision permalink and statement ID. If the statement is already correct and fully referenced, record its existing revision and verify those references against the same standard.
4. Run `npm run source:fetch -- --refresh Q43` (replace Q43 with the affected entity IDs) to retrieve the updated Wikidata information, then `npm run build`. Commit the pinned snapshots, source manifest, binary, and evidence artifacts together. Keep raw snapshots immutable. When a Wikidata contribution is blocked or pending, use the reviewed override workflow below.
5. Run `npm run check` and `npm run evidence -- --base /path/to/trusted-main`. Review every evidence result and include the report with the pull request. A missing source, inaccessible supporting passage, conflicting value, or unresolved review remains non-passing.

Local matching rules, such as normalization and unofficial aliases, must be clearly identified as policy. They cannot establish a country fact or bypass source verification. The build checks `sources/accepted-inputs.json`; keep every pinned entity/input pair and its expected lookup behavior, and add compatibility fixtures for newly accepted inputs. Every input needs both namespaced and default lookup expectations. Changes to expected answers or fixture removal are flagged by the trusted-base checker and require explicit review against the base revision. The observation job runs proposed code, and a fresh verdict job compares only JSON results against protected base expectations, even when runtime data files are unchanged. Preserve accepted inputs and historical identities when preferred names or current codes change.

## Reviewed local overrides

`sources/reviewed-overrides.json` holds versioned review records. A record identifies the statement and reviewed revision, exact baseline and digest, proposed correction or evidence-only decision, scope and dates, three source passages, approval, issue, independence assessment and upstream state. Optional `acceptedReferenceUrls` lists explicitly reviewed URLs for the same primary document; fragment identifiers are ignored, but transport and query parameters are not guessed equivalent. Optional `acceptedReferenceItems` identifies reviewed Wikidata document items that may appear as stated-in (P248) citations. The supported properties are P30, P297, P298, P299, P576 and P1366 on existing statements consumed by the build. Unknown or unused targets fail when activated. Labels and unofficial aliases retain their separate matching policy.

`sources/review-approvals.json` maps review IDs to SHA-256 digests of their complete canonical JSON records. Compute a digest with `reviewDigest` from `src/overrides.ts`. Any edit to evidence, scope, value or approval changes that digest. An approval field in proposed JSON cannot authenticate itself: the PR checker uses only approval digests from the trusted base branch. Main requires build and policy checks but does not require an independent approving review. Maintainers can merge their own PRs. The maintainer merging a staged approval must review its evidence and exact digest; the gate does not authenticate that human decision. The separate activation PR still requires the digest to exist on the trusted base.

The rollout has two PRs. First merge the schema support, reviewed record and approval digest without activating it or changing generated artifacts. Then add its ID to `active` in `sources/override-activation.json`, increase `datasetVersion` in `sources/policy.json`, rebuild and check the artifacts. The trusted base now owns the approved digest. An evidence-only record preserves the country value while binding the reviewed evidence into the companion and binary digest. A correction applies to an in-memory copy; it never rewrites the Wikidata snapshot.

The checker rebuilds reviewed artifacts using trusted code and compares the full binary and companion, including entity fields and assignment date bounds. An unchanged manifest and policy (apart from dataset version) permit a narrowly scoped reviewed transition; unrelated source refreshes and compatibility-fixture changes still require review. A reviewed assertion does not certify the rest of the spike corpus. Offline findings cannot certify live upstream state.

Each live check compares the original reviewed statement with current Wikidata. Value, qualifier, rank or reference changes require review. Once the effective assertion and primary reference are accepted upstream, review the new revision and move the ID from `active` to `retired`, then run `npm run source:fetch -- --refresh Q43` for the affected entity and rebuild with a new dataset version. When the primary citation is already present at initial review, select the record as retired rather than active. Retired records retain source verification and must match the upstream assertion and primary reference. A refresh restricted to entities with selected reviews can use the scoped gate only when trusted rebuilding preserves every effective runtime fact and every unreviewed assertion apart from revision. Each changed snapshot must also match its complete live pinned Wikidata entity; offline mode cannot authenticate that provenance. Other source changes still receive the broader evidence review. Retiring a review does not require replacing its approved record when its effective value and primary reference are accepted unchanged. Rejected upstream proposals require reconsideration and cannot be activated. Keep the contribution discussion and final revision in the issue.

The Turkey review for issue #2 is staged with no active IDs. It records the maintainer’s acceptance of the three publications and explicitly preserves uncertainty about independence of their underlying measurements.

## What a data pull request must include

- The affected Slackwater inputs and intended answers, including any dates, ambiguity, or coverage limits.
- The exact Wikidata entity, statement IDs, and revision permalinks used by the sync.
- The primary source and at least two other quality corroborating sources for each assertion, with supporting passages or table locations, dates, and assessed independence. Identify the primary reference contributed to Wikidata or explain why it is pending.
- An explanation of disagreements, date precision, and any unresolved assertions. Unresolved entries stay outside verified release coverage.
- The dataset version change, generated artifact changes, compatibility fixtures, and evidence report. Explain any change to an existing answer; retain old accepted spellings and dated meanings.
- Applicable upstream data licenses and notices, following [DATA_LICENSE.md](DATA_LICENSE.md). The [MIT license](LICENSE) covers code and documentation.

The evidence checker validates pointers, value bindings and exact approved review records; it does not interpret source passages or establish source independence automatically. Maintainers make those decisions during review. A green build or a reference count alone cannot certify a dataset. The spike's existing corpus remains unreviewed until it satisfies this policy.

## Review checks

Check reader behavior against immutable base expectations, including code-only changes with byte-identical data. Changing the proposed fixture must not hide a changed answer. Require default lookup cases as well as namespaced cases for every input. Check shared-reference expansion in the binary verifier and in the semantic readers that consume its output; caching alone must not bypass the work bound. Keep proposed code out of the verdict job and require complete, unique observed cases. Include binary identity when checking equal-version freshness after rollback.

For unrelated PRs with byte-identical runtime artifacts, live drift and source outages remain visible as non-blocking findings (`blocking: false`). The report keeps `passed: false` when evidence needs review and separately reports `gatePassed: true` for a safe maintenance PR. Data changes still require all selected reviews to pass; offline mode never certifies live evidence. Reviewed corpora require an explicit trusted `--base` for the evidence command, for example `npm run evidence -- --base /path/to/main`.

To re-baseline an active review after another upstream edit, stage a replacement record with a new ID and its approval digest while keeping the original selected record and pinned snapshots intact. Multiple staged records may name the same statement; selecting two for one target is rejected. After the replacement approval merges, switch activation to that ID and pin the reviewed revision in a follow-up PR. Unchanged-artifact drift findings cannot block the staging PR. Changes to effective runtime facts or compatibility expectations still require their separate review.

Factual corrections that change accepted lookup answers remain non-passing under the protected compatibility fixture. A separate trusted fixture-approval route is outside the current overlay workflow. Recording or testing such a correction locally does not authorize a changed answer in a protected release. Withdrawing an incorrect active correction likewise requires explicit compatibility and evidence review. Maintainers record upstream rejection manually; the checker does not poll discussion pages or infer acceptance from an unchanged baseline.

## Name evidence readiness diagnostics

The existing reviewed override and trusted approval workflow remains the approval path for its supported statement properties. The optional `sources/evidence-reviews.json` ledger (`{ "schemaVersion": 1, "reviews": [] }`) provides readiness diagnostics for assertions outside that path, especially names and aliases. Requests already carrying a reviewed override use that workflow. A readiness record targeting one is reported as unsupported; it cannot replace its approval. The ledger cannot activate an override, approve a finding, or make the gate pass. An absent ledger means no readiness work is recorded. Every proposed unreviewed request receives a diagnostic, even when binary artifacts are unchanged. Unknown ledger IDs remain visible as incomplete diagnostics without erasing evidence findings.

Each record uses `id` and `requestDigest` (SHA-256 of `canonical(request)`, via `requestDigest` in `src/evidence.ts`) to bind the exact value, revision, qualifiers and policy. Include `statement: { property, id, expected }`. Label and alias readiness accepts only monolingual text statements with the requested language on P1448 (official name), P1449 (nickname), P2561 (name), P1705 (native label), or P1813 (short name). An ISO code or other string statement cannot prove a name. Names need a referenced name statement: labels and aliases cannot hold references. A statement for a different spelling does not establish the requested alias.

Include `sources`, each with `url`, stable originating `publisher` identity, `role` (`authority` or `corroboration`), a short supporting paraphrase or permitted excerpt in `passage`, `location`, and `retrieved` date (`YYYY-MM-DD`). For these name-readiness records, require one authority and at least three corroborating publishers. Existing reviewed overrides retain the approval path above; these diagnostics do not revise staged approvals. The diagnostic rejects repeated URLs and publisher identities and checks those URLs against the statement references at pinned and current revisions. URL fragments are ignored; transport and query parameters remain significant. Offline diagnostics always retain a missing live-current-reference check and cannot reach ready status. This is a diagnostic for the supplied name evidence, not a new reference requirement for existing reviewed overrides. A human must assess publisher independence, passage authenticity and reliability; explain that assessment in `independenceExplanation`.

Record `reviewer`, `issue`, review `permalink`, and `reviewedAt` date. These fields provide traceability, not authentication. Only an identical record already present in the read-only trusted `--base` ledger receives a trusted-attestation diagnostic; proposed JSON cannot approve itself. Complete records report only `ready-for-human-review`. Protect the base checkout and verdict code as with existing approvals. Reader-result mode does not inspect this diagnostic ledger or change its compatibility verdict.

`source:fetch` without `--refresh` authenticates existing pins and fetches newly mapped entities only. Use `--refresh Q43 Q145` for selected entities or bare `--refresh` for all entities. Existing historical entities are retained deliberately. New compatibility fixture entries record candidate behavior for explicit review; generating them does not approve their correctness. The initial `accepted-methods.json` fixture seeds conversion and entity-assignment coverage; after it reaches the trusted base, proposed method results and fixture edits are checked independently of the PR.
