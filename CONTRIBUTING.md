# Contributing

c5y-n8r provides fast library access to country information from pinned Wikidata snapshots and explicitly reviewed local contributions. Wikidata is the upstream source: information it lists can be included without independent certification by this project. Our first goal is usable, traceable coverage of the country inputs required by Slackwater.

## Admit upstream data and track its quality

Acceptance requires the intended Wikidata entity, immutable revision and digest, faithful handling of values, ranks and qualifiers, reproducible artifacts, and preserved lookup compatibility. It does not require a primary source, a reference count, or a completed independent review for every upstream statement, label or alias. A source match establishes provenance, not factual certification. Upstream errors can appear in our dataset.

We undertake asynchronous research for facts whose upstream evidence is missing or weak. Suspected errors and changes since the pinned revision are also quality follow-up work. Shipping source-backed data does not wait for that research to finish. Keep automatically detected gaps in reports and record researched weaknesses in issue follow-ups, investigate asynchronously, improve Wikidata, then refresh the affected entities and release a new dataset version. An incomplete quality review does not exclude an otherwise source-backed value. Selecting additional genuine upstream spellings through the consumer inventory or language-name list is ordinary ingestion, not a claim of complete geographic or temporal coverage. Do not erase findings or label unreviewed data independently verified to get a passing build.

Missing historical dates remain unknown. Trusting a current code claim does not establish its introduction date, and a country existence date cannot supply a code assignment date. Preserve temporal uncertainty, competing identities, historical candidates and deprecated claims according to their explicit interpretation rules.

## Investigate and improve Wikidata

When investigating a quality issue, prefer the responsible standards body or issuing authority. Read supporting passages and record URLs, locations, dates, assessed independence and disagreements. Mirrors and sites derived from Wikidata are not independent corroboration. Search snippets and AI answers are not evidence. Existing reviewed local overrides require the source review described below; optional name-readiness records use one authority and three independent corroborating sources. These research standards are not prerequisites to importing existing Wikidata data.

Before proposing a Wikidata correction on our behalf, double-check the assertion against three other independent sources and add the supporting references to the relevant statement where supported. Preserve valid existing references and follow Wikidata's contribution rules. If support is incomplete, record the open question. The pinned upstream value can remain available while research proceeds. A confirmed error needs an explicit correction or withdrawal with compatibility review; an advisory flag is not a reason to ignore it.

## Sync upstream data and preserve compatibility

1. Check the Wikidata entity and statement, qualifiers, rank and existing references. Confirm the entity represents the intended country or historical identity. For an existing upstream value, record its revision and references without requiring a new research project. For a proposed upstream edit, record the source checks and contribution discussion.
2. Record the resulting revision permalink and statement ID, or the existing revision when no edit is needed.
3. Run `npm run source:fetch -- --refresh Q43` for the affected entities, then `npm run build`. Commit the pinned snapshots, manifest, binary and evidence artifacts together. Keep raw snapshots immutable and increase the dataset version when runtime artifacts change.
4. Update issue mappings and run `node scripts/refresh-evidence-issues.mjs` to bind the tracker to the current evidence digest and dataset version.
5. Run `npm run check` and `npm run evidence -- --base /path/to/trusted-main`. Include the report and quality follow-up links with the PR. Missing independent supporting sources are advisory. Invalid source bindings, unauthenticated new or changed pins, incompatible behavior and unapproved local corrections remain blocking. For byte-identical artifacts and exactly unchanged requests, the trusted base can supply prior provenance during a pinned-source outage; the outage remains an advisory, not a fresh authentication claim.

Local matching rules, such as normalization and unofficial aliases, must be identified and reviewed as policy. They cannot be passed off as statements made by Wikidata. Keep every pinned entity/input pair and its expected lookup behavior in `sources/accepted-inputs.json`, and add namespaced and default lookup expectations for new inputs. Changes to existing answers require the authenticated ISO date-correction route or explicit trusted review; fixture removal requires explicit trusted review. The observation job runs proposed code; a fresh verdict job compares only its JSON results against base expectations. Preserve accepted spellings and historical identities when preferred names or current codes change.

### Temporal ingestion and rollback

A single ISO-assignment P580 `somevalue` uses the existing unknown-start bounds in the binary. The evidence companion preserves the explicit qualifier, and its digest binds that evidence into the binary. P1319, P1326, P8555, P8554 and P12506 companion bounds are unsupported on ISO claims and stop ingestion, whether the start is known, unknown or absent; they cannot be silently discarded. P580 `novalue`, unknown ends (P582), unknown dissolution dates and contradictory date values are unsupported.

For every ISO assignment with a known start or end, `npm run build -- --extend-accepted-inputs` appends namespaced and default observations immediately before the start window, on its first and last days, and immediately after it. End windows have observations on their first and last possible inclusive end days and the following exclusive days. Existing inputs that gain dates receive these observations too. Normal builds require these observations and replay all previously accepted cases, so ordinary builds reject a changed dated answer when a protected known start becomes unknown. These are unreviewed behavior baselines, not certification of a source date. Source date corrections use `npm run build -- --refresh-temporal-lookups --base /path/to/main`. This refresh preserves every query and accepted input, recomputes results, appends new boundary cases, and writes the artifacts. It requires an increased dataset version, a newer Wikidata revision and only permits P580/P582 changes on existing ISO statements. Entity facts, code identities, ranks, withdrawal versus deprecation handling, aliases, local policy and selected reviews remain protected. The trusted-base evidence and reader-verdict checks rebuild the artifact themselves and authenticate changed full Wikidata snapshots at their pinned revisions. Offline checks cannot approve a correction. Merge this support before submitting a data correction, since CI and the external policy controller execute base-branch code.

Merge ingestion support before a data PR that requires it: the evidence job uses the base branch's builder. Binary readers need no format change for unknown starts. Rolling back the builder must retain all accepted-input fixture rows; a blanket revert that removes them fails the append-only gate. For existing inputs, an authenticated earlier snapshot and its manifest entry can be restored manually only if all accepted inputs and answers survive; increase the dataset version when artifacts change. `source:fetch --refresh` fetches the latest revision and is not a rollback command. Newly admitted inputs cannot currently be withdrawn through the protected fixture. If no compatible earlier pin exists, keep the ingestion support and roll forward; a higher dataset version alone does not authorize removing inputs or changing protected answers outside the date-only route.

## Approve changes to local policy

Review the exact policy change before it ships. In the first PR, add approval digests to `sources/review-approvals.json` without changing runtime data. Use `local-policy-transition` for the SHA-256 of `canonical({ before, after })`, where both objects are from `sources/policy.json` with `datasetVersion` and `aliases` removed. Coverage text is included because it is part of the runtime artifact. Use `local-policy-request:<id>` for the SHA-256 of the complete canonical evidence request for each new or changed local rule, including a source spelling used as a local code. For a withdrawal, use `local-policy-withdrawal:<id>` and hash the complete old request. These digests include the pinned revision. Remove used approvals in the activation PR. When reverting an activation, keep those keys deleted. The checker blocks adding or replacing approval keys alongside changes to runtime artifacts. See [the Slackwater approval inputs](docs/slackwater-policy-approval.json) for an example. The transition digest covers policy declarations, and request digests cover individual local assertions. Genuine Wikidata labels and aliases still use the source-fidelity checks.

After the approval merges, submit the policy and regenerated artifacts in a second PR. The checker reads digests only from the trusted base and still requires source authentication, artifact reproduction, versioning, and lookup compatibility. The approval records a maintainer decision about the local rule and does not certify it as a Wikidata fact.

## Reviewed local overrides

`sources/reviewed-overrides.json` holds versioned review records. A record identifies the statement and reviewed revision, exact baseline and digest, proposed correction or evidence-only decision, scope and dates, three source passages, approval, issue, independence assessment and upstream state. Optional `acceptedReferenceUrls` lists explicitly reviewed URLs for the same primary document; fragment identifiers are ignored, but transport and query parameters are not guessed equivalent. Optional `acceptedReferenceItems` identifies reviewed Wikidata document items that may appear as stated-in (P248) citations. The supported properties are P30, P297, P298, P299, P576 and P1366 on existing statements consumed by the build. Unknown or unused targets fail when activated. Labels and unofficial aliases retain their separate matching policy.

`sources/review-approvals.json` maps review IDs to SHA-256 digests of their complete canonical JSON records. Compute a digest with `reviewDigest` from `src/overrides.ts`. Any edit to evidence, scope, value or approval changes that digest. An approval field in proposed JSON cannot authenticate itself: the PR checker uses only approval digests from the trusted base branch. Main requires build and policy checks but does not require an independent approving review. Maintainers can merge their own PRs. The maintainer merging a staged approval must review its evidence and exact digest; the gate does not authenticate that human decision. The separate activation PR still requires the digest to exist on the trusted base.

The rollout has two PRs. First merge the schema support, reviewed record and approval digest without activating it or changing generated artifacts. Then add its ID to `active` in `sources/override-activation.json`, increase `datasetVersion` in `sources/policy.json`, rebuild, run `node scripts/refresh-evidence-issues.mjs`, and check the artifacts. The trusted base now owns the approved digest. An evidence-only record preserves the country value while binding the reviewed evidence into the companion and binary digest. A correction applies to an in-memory copy; it never rewrites the Wikidata snapshot.

The checker rebuilds reviewed artifacts using trusted code and compares the full binary and companion, including entity fields and assignment date bounds. Every data PR uses the same trusted source-rebuild path. Ordinary upstream refreshes use provenance checks, selected local reviews retain their approval controls, and append-only fixture additions preserve all trusted expectations. A reviewed assertion does not certify the rest of the spike corpus. Offline findings cannot certify live upstream state.

Each live check compares the original reviewed statement with current Wikidata. Value, qualifier, rank or reference changes require review. Once the effective assertion and primary reference are accepted upstream, review the new revision and move the ID from `active` to `retired`, then run `npm run source:fetch -- --refresh Q43` for the affected entity and rebuild with a new dataset version. When the primary citation is already present at initial review, select the record as retired rather than active. Retired records retain source verification and must match the upstream assertion and primary reference. Retirement uses the same trusted rebuilding and source-provenance checks as other data changes; the selected retired review must still match the effective upstream assertion. Each changed snapshot must also match its complete live pinned Wikidata entity; offline mode cannot authenticate that provenance. Other source changes receive the ordinary provenance and compatibility checks. Retiring a review does not require replacing its approved record when its effective value and primary reference are accepted unchanged. Rejected upstream proposals require reconsideration and cannot be activated. Keep the contribution discussion and final revision in the issue.

The Turkey review for issue #2 is staged with no active IDs. It records the maintainer’s acceptance of the three publications and explicitly preserves uncertainty about independence of their underlying measurements.

## What a data pull request must include

- The affected Slackwater inputs and intended answers, including any dates, ambiguity, or coverage limits.
- The exact Wikidata entity, statement IDs, and revision permalinks used by the sync.
- Existing reference links and known quality flags. For facts lacking adequate evidence, link the asynchronous research task; completing it is not required for importing an existing Wikidata assertion. Local overrides retain their separate evidence requirements.
- An explanation of disagreements, date precision and unresolved identity or mapping questions. Distinguish missing references from an absent upstream value or ambiguous identity.
- The dataset version change, generated artifact changes, compatibility fixtures, refreshed evidence issue map, and evidence report. Explain any change to an existing answer; retain old accepted spellings and dated meanings.
- Applicable upstream data licenses and notices, following [DATA_LICENSE.md](DATA_LICENSE.md). The [MIT license](LICENSE) covers code and documentation.

The evidence gate enforces source fidelity and compatibility. Quality diagnostics do not interpret passages or certify the dataset. An accepted source-backed value can still lack independent review.

## Review checks

Check reader behavior against immutable base expectations, including code-only changes with byte-identical data. Changing the proposed fixture must not hide a changed answer. Require default lookup cases as well as namespaced cases for every input. Check shared-reference expansion in the binary verifier and in the semantic readers that consume its output; caching alone must not bypass the work bound. Keep proposed code out of the verdict job and require complete, unique observed cases. Include binary identity when checking equal-version freshness after rollback.

Check that matching upstream assertions are admitted without reference-count or independent-review prerequisites. Missing references and current upstream drift remain visible as non-blocking findings. Mismatched pinned values, unsupported transformations, unapproved local overrides and changed protected answers outside the authenticated date-only route must fail. Data changes require trusted artifact reproduction and an increased dataset version. Changes to local coverage declarations, reader requirements or interpretation policy need separate review; Wikidata provenance cannot authorize those declarations. Offline checks cannot authenticate live pinned revisions. Reviewed corpora require an explicit trusted `--base` for the evidence command, for example `npm run evidence -- --base /path/to/main`.

To re-baseline an active review after another upstream edit, stage a replacement record with a new ID and its approval digest while keeping the original selected record and pinned snapshots intact. Multiple staged records may name the same statement; selecting two for one target is rejected. After the replacement approval merges, switch activation to that ID and pin the reviewed revision in a follow-up PR. Unchanged-artifact drift findings cannot block the staging PR. Changes to protected compatibility expectations require the authenticated date-only route or separate trusted review. Source-backed factual changes use the ordinary ingestion checks; removing a selected local correction also requires explicit review.

ISO date-only corrections can change accepted answers through the source-authenticated temporal refresh above. Other factual corrections that change accepted lookup answers remain blocked; the temporal route cannot approve identity, rank, alias or local overlay changes. Withdrawing an incorrect active correction likewise requires explicit compatibility and evidence review. Maintainers record upstream rejection manually; the checker does not poll discussion pages or infer acceptance from an unchanged baseline.

## Optional name evidence research diagnostics

The reviewed override workflow applies to local corrections and optional evidence attestations, not ordinary Wikidata imports. The readiness ledger is asynchronous research work and is not a release prerequisite. The optional `sources/evidence-reviews.json` ledger (`{ "schemaVersion": 1, "reviews": [] }`) provides readiness diagnostics for assertions outside that path, especially names and aliases. Requests already carrying a reviewed override use that workflow. A readiness record targeting one is reported as unsupported; it cannot replace its approval. The ledger cannot activate an override, approve a finding, or make the gate pass. An absent ledger means no readiness work is recorded. Every proposed unreviewed request receives a diagnostic, even when binary artifacts are unchanged. Unknown ledger IDs remain visible as incomplete diagnostics without erasing evidence findings.

Each record uses `id` and `requestDigest` (SHA-256 of `canonical(request)`, via `requestDigest` in `src/evidence.ts`) to bind the exact value, revision, qualifiers and policy. Include `statement: { property, id, expected }`. Label and alias readiness accepts only monolingual text statements with the requested language on P1448 (official name), P1449 (nickname), P2561 (name), P1705 (native label), or P1813 (short name). An ISO code or other string statement cannot prove a name. This optional research diagnostic needs a referenced name statement because labels and aliases cannot hold references. Importing a Wikidata label or alias does not require one. A statement for a different spelling does not establish the requested alias.

Include `sources`, each with `url`, stable originating `publisher` identity, `role` (`authority` or `corroboration`), a short supporting paraphrase or permitted excerpt in `passage`, `location`, and `retrieved` date (`YYYY-MM-DD`). For these name-readiness records, require one authority and at least three corroborating publishers. Existing reviewed overrides retain the approval path above; these diagnostics do not revise staged approvals. The diagnostic rejects repeated URLs and publisher identities and checks those URLs against the statement references at pinned and current revisions. URL fragments are ignored; transport and query parameters remain significant. Offline diagnostics always retain a missing live-current-reference check and cannot reach ready status. This is a diagnostic for the supplied name evidence, not a new reference requirement for existing reviewed overrides. A human must assess publisher independence, passage authenticity and reliability; explain that assessment in `independenceExplanation`.

Record `reviewer`, `issue`, review `permalink`, and `reviewedAt` date. These fields provide traceability, not authentication. Only an identical record already present in the read-only trusted `--base` ledger receives a trusted-attestation diagnostic; proposed JSON cannot approve itself. Complete records report only `ready-for-human-review`. Protect the base checkout and verdict code as with existing approvals. Reader-result mode does not inspect this diagnostic ledger or change its compatibility verdict.

`source:fetch` without `--refresh` authenticates existing pins and fetches newly mapped entities only. Use `--refresh Q43 Q145` for selected entities or bare `--refresh` for all entities. Existing historical entities are retained deliberately. New compatibility fixture entries record candidate behavior for explicit review; generating them does not approve their correctness. The initial `accepted-methods.json` fixture seeds conversion and entity-assignment coverage; after it reaches the trusted base, proposed method results and fixture edits are checked independently of the PR.

The external controller checks the proposed data checkout using only base-branch code and dependencies. Reader verdicts require artifact reproduction and authenticate changed pins in batches of eight, with a shared network budget of at least 90 seconds, scaled by changed-pin batches and local requests, capped at ten minutes. The report includes `authenticationBudgetMs`; the controller allows twelve minutes for the verdict and CI allows fifteen for the verdict job. An outage fails authentication; retry the check. Unchanged pins with no new or changed local requests require no network access in this verdict. Local alias changes can need live source checks even when their entity pin is unchanged. CI and the controller inspect the PR merge tree. The controller verifies its two parents against the exact current base and head; unknown mergeability is polled briefly and remains pending if GitHub has not finished computing it. A stale or missing merge commit fails closed.

The correction route requires a newer pinned revision than the base. Current upstream drift remains advisory after pinned authentication; the evidence job reports it for follow-up. The reader verdict applies the same source-fidelity policy to inherited or explicitly approved removals and local rules, while preserving all protected queries and checking approval for new or changed local aliases.

If GitHub mergeability remains unknown after the bounded polling, the status stays pending. Retry the check for a temporary computation delay. If the protected branch advanced, update the PR branch and obtain fresh observations; reruns retain their original merge SHA. A missing or stale merge commit never produces approval.

Controller concurrency is grouped by head commit, with [GitHub’s bounded queue](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency) enabled, so unrelated PRs do not discard each other’s checks. Discard stale completion events before polling mergeability or writing a status, and recheck head, base and run identity after polling. When rolling the builder forward after older tooling admitted dated inputs, run `npm run build -- --extend-accepted-inputs` before merging the roll-forward.

The merge-input producer records `reader-binding.json` separately from schema-2 observations so ingestion support can bootstrap against the existing checker. Trusted jobs check out its exact merge parent, and the controller authenticates the binding against the current protected branch tip, head, GitHub test-merge SHA and Git parents. GitHub’s recorded PR or run base SHA can lag the actual merge parent; it cannot select the trusted verifier. If the protected branch advances after observation, refresh the PR branch so CI records a fresh merge. Controller tests cover lagging recorded bases, missing or forged bindings and stale PR events.

Merge refs are derived by the workflow from Git parents without executing a proposed repository script. Before rolling forward after a builder rollback, also check that refreshed snapshots contain no temporal forms the restored builder cannot interpret; fixture extension cannot make unsupported bounds valid.

Date-correction PRs contain only eligible ISO date changes. To undo a correction, fix Wikidata and pin a newer revision; restoring an older answer-changing pin is outside this route. In-flight PRs must update their branch after this support merges to generate the merge-input job and binding artifact. A rerun of an older workflow retains that workflow and its original merge SHA. Branch protection requires up-to-date branches, so a previously green status cannot authorize merging against a newer protected base.
